# Visual and rendering requirements

Read before public CSS, layout, typography, motion, diagrams, PCB artwork, or SVG preparation changes. These exact constraints override generic skill suggestions; the approved PCB pointer lens is an explicit exception to the general ban on cursor effects. Generated PCB geometry is immutable: generic advice to simplify or reroute artwork does not apply to it.

## Visual Rules

The desired impression is cold competence: controlled, sharp, calm, confident, and not sterile.

Use:

- Near-black or deep-charcoal backgrounds.
- Slightly lighter surface layers.
- Soft off-white primary text.
- Muted cool-grey secondary text.
- Low-contrast borders.
- One restrained icy-blue, steel-blue, or desaturated-cyan accent.
- Typography-led hierarchy.
- Spacious but purposeful layouts.
- Subtle hover and reveal motion.
- Exposed public content uses proportional dark readability underlays that follow each rendered text line and fade softly to transparent well outside its curved edge; larger text receives a broader fade. Transparent secondary buttons use one underlay around the complete control. Do not add underlays beneath content already enclosed by an opaque surface.
- Hard-cornered buttons.
- Hard-cornered card surfaces with slightly thicker borders.
- Light-blue primary buttons with black text, an offset striped shadow shape, and a slightly larger/separated hover state.
- Button shadow shapes use solid deep colors with 3px borders and black diagonal negative stripes; do not make them translucent.
- Primary button hover states must keep black text.
- `Start a Conversation` uses the same primary button face with a pink striped shadow shape.
- Project `View Case Study` actions use a pointed arrow-style blue button with horizontal hover motion.
- Service item tags are plain inline text separated by large accent dots, not pills.

Avoid:

- Bright gradients.
- Neon cyberpunk styling.
- Decorative blobs.
- Fake terminal aesthetics.
- Code rain.
- Heavy glassmorphism.
- Multiple accent colors.
- Rounded pill buttons for primary actions.
- Rounded card surfaces.
- Pill-shaped service tags.
- Scroll-jacking, parallax, magnetic buttons, cursor effects, or long intro animations.

Every design choice should improve hierarchy, readability, comprehension, navigation, trust, or interaction feedback. If it does not, remove it.

## Rendering invariants

- Keep global visual tokens in `app/globals.css`.
- Keep PCB readability underlays attached only to the immediate visible content piece—such as a heading, paragraph, list item, label, metric, link, table value, or transparent button—never to the grid, row, cell container, form, or column that positions it. Wrapped text must use the shared semantic `CircuitUnderlay` inline-block wrapper. Its single canonical content layer determines layout; its inert paint source is absolutely positioned and cannot contribute intrinsic size; derive the paint source's text-shaped layout from a data attribute rather than duplicating live React children or nested elements. Force its generated text transparent and put the complete shadow layer at a negative stack level. Do not isolate individual underlay wrappers: all exposed content within one section content plane must share a stacking context so a later heading shadow also remains behind earlier siblings such as eyebrows. Put canonical content at a positive foreground level so shadow opacity cannot overlay or dim glyphs. `box-decoration-break: clone` gives the source each rendered line's rounded geometry. The source color must match the section's declared background color, including base, soft, surface, and blue impact sections. Preserve the current strengths of `0.91` for body/heading, `0.8372` for compact content, and `0.6006` for the transparent secondary-button source; these are the approved 30% increase over the preceding treatment. Extend the source beyond the content with a proportional zero-blur spread before applying the Gaussian blur; do not use padding for this extension, because it changes wrapping. Scope unrelated descendant and pseudo-element selectors to their actual component classes. Compact, body, and heading content use progressively larger source extension, radius, strength, and blur. Do not join a semi-transparent fragment fill to a separate shadow, use inset/outer edge shadows, or use a paragraph/layout-box pseudo-element. If the host already uses a pseudo-element for responsive labels or decoration, preserve it and wrap only the visible value. Transparent secondary buttons use one blurred pseudo-element around the complete button rectangle beneath its text and border. Every exposed standalone rule, open-sided border group, transparent grid line, and small transparent primitive such as the case-back arrow must use an exact stroke-shaped paint source with a section-background-colored shadow that begins at the approved strength and spreads/fades on every side of that stroke. Keep all such sources in one behind-content stacking plane so overlapping halos never dim canonical content. Do not give an open-sided element a rectangular or outside-only enclosure shadow, and do not synthesize shadows along absent sides intended to remain flush with the background. When responsive CSS removes a border, remove its paint source too. Only fully bordered opaque enclosures—cards, diagram canvases, and form fields—use an outside-only shadow: use the surrounding section background color and the same approved strength, allowing the opaque fill to hide the inward half. Never use a generic black elevation shadow, attach either treatment to a broad positioning parent, animate these filters/shadows, create section-level foreground layers, or apply readability underlays inside an opaque surface that already hides the PCB artwork.
- Keep public typography on the centralized `--font-primary` Segoe UI system stack so local and deployed rendering use the same declared font path; do not reintroduce an unloaded `Inter` label or a separate environment-specific webfont.
- Every case-study diagram must use the shared `case-diagram` foreground layer and opaque `case-diagram-surface` canvas. The page circuit pattern and its pointer glow may remain visible around a diagram, but must never show through or paint over the diagram canvas.
- Keep the public PCB pointer response as a bounded 410px native SVG lens with the established base glow ending at a 165px radius and a reserved 40px outer ring for perimeter-wave leaks. Each background is a paired asset: the semantic SVG preserves every renderer primitive, group, stable ID, class, ownership label, and geometry attribute for future targeted animation; a separate exact-geometry spatial lens projection may compound primitives only within local cells. The PCB Art Generator render is the immutable source of visual geometric identity: preparation and optimization must not add, remove, omit, reroute, reconnect, reshape, simplify, or procedurally reinterpret any generated line, circle, marker, chip, path, or other form. Styling adjustments may change palette/background/stroke treatment only without changing authored forms or topology. Never turn ignored line fills into active fills, recolor negative markers into foreground geometry, connect independent subpaths, or discard small circles/markers. Attach one hidden `pcb-depth-geometry` definition containing a translated reference to the unchanged `pcb-semantic-source`; this records depth identity without rendering or duplicating primitive data. For public display, measure native bounds of the unchanged spatial paths once per source, then compile genuinely local vector SVG resources at most 512 CSS px in each dimension per changed layout. Retain full original path data for every intersecting path, with conservative stroke and depth margins; clip only at resource boundaries. Paint positive vectors directly with section-aware palettes, with 1px-down depth first and opaque main last. Use bounded luminance masks only for the negative cutouts; retain ordered luminance painting for any mixed-positive/negative path. Source assets remain immutable and Storage-owned. Do not return to page-height images/masks or named views that retain the full page paint tree. Use `#0f1115` main / `#1c2126` depth on dark sections, `#090d11` main / `#29323a` depth on grey or muted sections, and `#0e325f` main / `#315686` depth on blue impact sections.
