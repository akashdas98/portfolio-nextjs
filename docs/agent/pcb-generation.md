# PCB generation procedure

Use this procedure whenever a user asks to generate or regenerate PCB artwork for a portfolio page. The renderer checkout is `E:/Documents/Projects/PCB Art Generator`; its production entry point is `generate_pcb.py`. Read that checkout's `AGENTS.md` production-use section and `docs/PRODUCTION_USE.md` for the current CLI contract. Do not edit the renderer merely to generate art.

1. Identify each affected public page. At the normal, unconstrained desktop layout (1440px browser viewport, default zoom), wait for the actual page content to render, then measure the complete PCB-bearing page region (`main.public-circuit-page`), including all of its sections. Use that region's **current measured width and height** as the page's individual `--aspect-ratio W:H`. Record the measurements. Do not use only the first viewport or include a separate footer outside the PCB region. Historical ratios and SVG viewBoxes are evidence only; do not reuse them without remeasurement. Generate each page independently. Responsive layouts subsequently fit, crop, or zoom the one authored composition through the existing public circuit renderer; do not generate separate phone/tablet geometry unless explicitly requested.
2. Run `python generate_pcb.py --aspect-ratio W:H --scale <requested> --count 1 --out-dir <workspace-output>`, adding the exact user-requested `--main-chip-density-multiplier`, `--main-run-length-multiplier`, `--local-density`, and `--component-density` values as applicable. **Omit `--seed` unless the user supplies one.** Let the renderer choose and report its seed. Do not retry with another seed to hide an invariant failure. Write generated files inside the writable portfolio workspace; leave the generator checkout unchanged.
3. For site use, run the repository's `prepare:pcb-background` command on each raw SVG to create a semantic SVG and exact-geometry spatial lens SVG, then `attach:pcb-depth` on the semantic output. Preserve every source primitive, classification, ID, topology, cutout, and paint order. Confirm the prepared pair passes the existing asset validation and matches the source viewBox and counts. Apply the visual rules in `docs/agent/visual.md`; do not redesign geometry in the frontend.
4. The homepage pair is site-owned under `public/pcb-backgrounds/`. Case-study pairs are project-owned Supabase Storage assets referenced by validated project documents. Keep case-study iterations local until the user explicitly approves promotion **for each project**. Before local iteration, mark its `CONTEXT.md` ledger row and `docs/agent/cms-promotion-status.json` entry `awaiting user approval`; do not push `main`. After approval, upload and verify both Storage objects, update the document and aligned seed/migration, remove local project duplicates, and restore `verified complete` only after remote verification.
5. Inspect the affected page composition and responsive fitting, and verify that static art, desktop lens, and touch behavior still use the matched semantic/lens pair. Record actual measurements, generated seeds, asset dimensions, validation, and any pending review or promotion in the task checkpoint. The renderer's production-use request itself does not call for its release tests or development handoff bundle.
